## Project

App funcional: home, biblioteca, detalle, reproductor, salón de la fama, login, about + contacto, 5 juegos jugables (Asteroids, Tetris, Arkanoid, Snake, Frogger) con leaderboard real en Supabase. Buenas prácticas:

- Una spec por cambio: `specs/NN-nombre.md`. Crear con `/spec`, implementar con `/spec-impl`.
- Cabecera: Estado, Depende de, Fecha, Objetivo. Secciones: Por qué, Alcance (dentro/fuera), Plan, Criterios de aceptación, Decisiones, Riesgos.
- Plan de implementación: cada paso lleva lista `Acciones` + lista `Verificaciones`. Formato en `.claude/rules/spec-plan-format.md` (la skill `/spec` es externa y no se edita).
- No salir del alcance; lo extra va a "Fuera de alcance" / spec futura.
- Un commit por paso (`NN-nombre: Paso N`). Al terminar, Estado → Implementado.

## Commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` / `npm start` — build / serve
- `ALLOWED_DEV_ORIGINS=<ip> npm run dev` — permite abrir el dev server desde el móvil en la LAN (`next.config.ts`; lista separada por comas, vacío por defecto).
- `npm run lint` — ESLint (flat config)
- `npm run check:secret-client` — falla si `createAuthActionClient` (clave secreta) se usa con `.from(`/`.rpc(` en `app/` o `lib/` (SPEC 20).
- `npm run perf` — mide FPS y JS/frame de los 5 juegos × skins con CPU ×1/×6 (Playwright, Chromium con ventana; requiere `npm run dev` activo; `PERF_URL`, `PERF_GAMES=a,b`, `PERF_HEADLESS=1`); sale con código 1 si algún caso con ×6 queda <58 FPS (SPEC 14).
- Sin test runner en la app Next. Prettier + `prettier-plugin-tailwindcss` (`.prettierrc.json`).
- App Angular (SPEC 24, desde `angular/`): `cd angular && npm start` (dev en `:4200`; ejecuta también las rutas Express de `src/server.ts`) · `npm run build` (SSR; sirve con `PORT=4300 node dist/arcade-vault-angular/server/server.mjs`) · `ng test --watch=false` · `ng lint`. `prestart`/`prebuild` copian `../public` a `angular/public/games/` (el builder no admite assets fuera del workspace; la copia está en `.gitignore`). `angular/.env` (ignorado): `SUPABASE_URL` y `SUPABASE_PUBLISHABLE_KEY` (mismos valores que `NEXT_PUBLIC_SUPABASE_*`; `SUPABASE_SECRET_KEY` no se usa). Servir el build en un host distinto de `localhost` exige añadirlo a `security.allowedHosts` de `angular.json`.

## Rutas (`app/`)

- `/`: home con hero, juegos destacados, features, actividad, estadísticas y CTA (`components/home/`).
- `/juegos`: biblioteca con todos los juegos de la tabla `games`, en tarjetas.
- `/juegos/[id]`: detalle de un juego (descripción, categoría, mejor puntuación, leaderboard). `[id]` = slug de `games.id`, p. ej. `asteroids`, `tetris`, `arkanoid`, `snake`, `frogger`. Lista completa en `references/implemented-games.md`.
- `/juegos/[id]/jugar`: reproductor con canvas y HUD (las opciones `live`, p. ej. skin, van dentro del HUD; las `restart`, en el overlay de pausa); guarda la puntuación al terminar solo con sesión (SPEC 18: `player_name` = username, sin input; el invitado ve "INICIA SESIÓN PARA GUARDAR TU PUNTUACIÓN" + botón a `/login` y esa puntuación se pierde; HUD "INVITADO" sin sesión). El `[id]` debe existir en `GAME_REGISTRY`. El menú de fin enlaza a `/salon-de-la-fama?juego=<id>`. Pinta el mando táctil con aspecto Gamepad MK-II (`components/touch-controls.tsx`, solo `@media (pointer: coarse)`; en móvil vertical va fijo al borde inferior para que el canvas ocupe el alto libre; direcciones sin tecla atenuadas, A/B con rótulo del registro, `.on` con teclado físico `isTrusted`) según `touchControls` del registro; emite `KeyboardEvent` sintéticos en `window` y se desactiva en pausa/fin. Con `cacheComponents` Next oculta la página en vez de desmontarla (Activity), por eso `GamePlayer` resetea su estado en el cleanup de un efecto.
- `/salon-de-la-fama`: mejores puntuaciones (top 12) con una pestaña por juego (`components/hall-of-fame.tsx`). `?juego=<id>` elige la pestaña inicial (desconocido → la primera).
- `/login`: acceso de jugador (`components/auth-form.tsx`, SPEC 16): iniciar sesión con email o usuario, crear cuenta (email de confirmación, sin sesión hasta confirmar), Google/GitHub, "¿Olvidaste tu contraseña?" (`components/forgot-password.tsx`) y "Jugar como invitado". Server Actions `signUp`/`signIn` en `app/login/actions.ts`. Con sesión redirige a `/`. `?error=oauth` muestra el fallo del callback; `?confirmed=1` muestra "Email confirmado" (enlace abierto en otro navegador). El nav con sesión muestra username + botón "Cerrar sesión".
- `/auth/callback` (`app/auth/callback/route.ts`): canjea el `code` (OAuth y enlace de confirmación) → `/`; fallo → `/login?error=oauth`; sin verificador PKCE (otro navegador) → `/login?confirmed=1`.
- `/perfil` (`components/profile-form.tsx`, SPEC 16): avatar grande, cambio de username (`updateUsername` de `useAuth()`; `A-Z0-9_` 3-10, único, en mayúsculas; las puntuaciones antiguas conservan su `player_name`) y botón "Cerrar sesión". Sin sesión → `/login`. SPEC 19: "Cambiar contraseña" desplegable (solo con identidad email; pide la actual, verificada en servidor, y cierra las demás sesiones) y "Zona peligrosa" → modal "Eliminar cuenta" (escribir el username; si no coincide, error al pulsar ELIMINAR; borra `auth.users`, `profiles` y `scores` en cascada → `/?cuenta=eliminada` con aviso). El nav muestra un bloque avatar + nombre (`components/account-menu.tsx`) que despliega "Perfil" y "Cerrar sesión"; en móvil solo el avatar. `/perfil` tiene "Guardar usuario", "Salir" (sin guardar) y "Cerrar sesión".
- `/auth/reset-password`: canjea el `code` de recuperación y muestra el formulario de nueva contraseña (`components/reset-password-form.tsx`); sin código válido → error + enlace a `/login`.
- `/about`: sobre la plataforma + formulario de contacto (Server Action `app/about/actions.ts`, Resend).

## Arquitectura

- `components/`: UI global (`nav`, `game-player`, `game-canvas`, `leaderboard`, `hall-of-fame`, `auth-form`, `library`, `game-card`…); `home/` y `about/` por sección.
- Juegos: un motor TS por juego en `lib/<juego>/` (`constants`, `engine`, `types`, `utils` + `entities`/`levels`/`sprites`/`skins` según juego). Contrato común en `lib/game-engine.ts` (`GameEngine`, `GameSnapshot`, `GameOption`, `TouchControls`). Registro en `lib/game-registry.ts` (`GAME_REGISTRY`, `getGameDefinition`): cada juego aporta un adaptador snapshot → HUD y su `touchControls` (d-pad + 0-2 acciones; los motores no deben filtrar `isTrusted`). Añadir juego = nuevo motor + entrada en el registro + migración seed (usar `/add-game`).
- Datos: `lib/games(.server).ts`, `lib/scores(.server).ts`, `lib/auth.tsx`, `lib/auth-validation.ts`, `lib/contact.ts`, `lib/home.ts`.
- Supabase: `lib/supabase/{client,server,admin}.ts`, tipos en `database.types.ts`, migraciones en `supabase/migrations/NNNN_*.sql` (tablas `games`, `scores`, `profiles`, un seed por juego). Env: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (solo servidor, SPEC 16; nunca `NEXT_PUBLIC_`), `NEXT_PUBLIC_SITE_URL` (SPEC 20: origen público sin `/` final, fija `emailRedirectTo`; obligatoria en prod, en dev `http://localhost:3000`; mismo valor que las Redirect URLs de Supabase; en `.env.template`) (+ clave de Resend); `.env*` ignorado por git.
- Auth (SPEC 16): `proxy.ts` en la raíz refresca la sesión (cookies, `@supabase/ssr`) y, desde SPEC 17, redirige a `/login` las rutas de `PROTECTED_ROUTES` (hoy solo `/perfil`) sin sesión, copiando las cookies del refresco; el resto es público (invitado intacto); no sustituye a RLS. `lib/supabase/admin.ts` (`server-only`, `service_role`) solo resuelve usuario → email vía `email_for_username` (ejecutable solo por `service_role`) y, desde SPEC 19, borra la cuenta con `auth.admin.deleteUser` en la Server Action `deleteAccount` (id siempre de `getUser()`). El trigger `on_auth_user_created` crea el `profiles.username` (saneado `^[A-Z0-9_]{3,10}$`, sufijo numérico si choca). `scores.user_id` lo pone la BD (`default auth.uid()`), `not null` desde SPEC 18 (el invitado no guarda); si se borra el usuario (`auth.users`), `profiles` y sus puntuaciones se borran en cascada (`on delete cascade`, migración `0013`). Migraciones `0010_auth_profiles` y `0011_profiles_policy_initplan` (policy con `(select auth.uid())`). Avatar: `components/avatar.tsx` (foto de `user_metadata.avatar_url`/`picture` o iniciales sobre fondo neón estable por username). Supabase: "Confirm email" activado, proveedores Google/GitHub y Redirect URLs `/auth/callback` y `/auth/reset-password`.
- Seguridad (SPEC 17): migración `0012_seguridad` (`revoke execute` de `rls_auto_enable()`; policy de insert de `scores` con `user_id is null or user_id = auth.uid()`, sustituida en SPEC 18 por `scores insert usuario`: solo `authenticated` con `user_id = (select auth.uid())`). Contraseña ≥8 con minúscula, mayúscula, dígito y símbolo (`validatePassword`/`PASSWORD_ERROR` en `lib/auth-validation.ts`, misma regla que Supabase). `createAuthActionClient()` (`lib/supabase/server.ts`, `server-only`): clave secreta + cabecera `sb-forwarded-for` (IP del jugador) solo para `auth.*` en `signUp`/`signIn`; salta RLS, nunca para datos; `over_request_rate_limit` → "Demasiados intentos…". Panel Supabase: rate limit sign-ups/sign-ins 10/5 min, IP Address Forwarding activo; leaked password protection no disponible en Free. Headers `X-Content-Type-Options`, `X-Frame-Options: DENY` y `Referrer-Policy` en `next.config.ts` (CSP/HSTS: spec futura). Checklist en `references/security/security-checklist.md`.
- Producción: Claude solo tiene acceso MCP a dev (`.mcp.json`); prod (Supabase + Vercel, `vercel.json`) se migra a mano con `references/deploy/prod-runbook.md`: el script único `references/deploy/prod-setup.sql` (migraciones 0001-0012 consolidadas) se pega en el SQL Editor de prod y se verifica con `references/deploy/verify-prod.sql`. Migraciones nuevas: pegar su SQL en prod a mano. Nunca claves/tokens de prod en el repo ni en Claude.
- `references/` (solo lectura): `started-games/` fuentes originales, `source-assets/` sprites, `templates/` maqueta UI.

### Al implementar código Angular

Aplica siempre, también al implementar una spec:

1. Antes de escribir una pieza >30 líneas o que toque varias clases, decide en 5–8 líneas piezas, responsabilidad única, dependencias y extensión (SOLID; skill `angular-solid`). Sin capas ni abstracciones prematuras.
2. Plantillas accesibles desde el principio al nivel `a11y`: leer la skill `angular-quality-a11y` antes de escribir cualquier plantilla; semántica nativa, nombre accesible, teclado, foco, contraste y tamaño de objetivo.
3. `docs: jsdoc` → JSDoc conciso en API pública, nada sobre lo evidente.
4. `tests: required` → crear el `.spec.ts` junto a cada pieza nueva o modificada, en el mismo paso, no en uno posterior.
5. Sintaxis y APIs de Angular: skill `angular-developer`. Solo APIs estables salvo petición o uso previo. Reutilizar los motores de `lib/` sin duplicarlos.
6. Antes de dar un paso por terminado, ejecutar `verify` y corregir. Informar qué se verificó y qué no.

### Al redactar specs Angular

Además de la plantilla de `/spec`, cada spec Angular incluye:

- **Diseño de clases**: piezas, responsabilidad de cada una y dependencias (SOLID).
- **Criterios de aceptación de accesibilidad** al nivel `a11y` (teclado, foco, etiquetas, contraste, tamaño de objetivo) para toda pantalla o componente con UI.
- **Plan de tests** por pieza (casos y límites), con su `.spec.ts` en el mismo paso del plan que la pieza.
- **Comando `verify`** como criterio de aceptación final.
